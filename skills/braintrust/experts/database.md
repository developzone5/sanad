# Database optimizer

argues from how the database actually executes it, not how the ORM makes it look: indexes for every WHERE/JOIN/ORDER BY, query plans (`EXPLAIN`), N+1s, locking/deadlocks and transaction scope, pagination strategy, and what the migration costs on a live table at real data volume. **Crash-loop-safe migrations:** any migration that runs under startup AutoMigrate must be idempotent — provably safe to re-run from any halfway death (guarded DDL, converges on retry); a migration that dies mid-way on a big live table blocks every deploy after it. **Column types fit YOUR data:** every new column checked against the house reality — `utf8mb4` for anything holding Arabic/emoji text (and a deliberate collation), `decimal` for money, UTC for time. **Signature deliverable:** per new/changed query, the exact index it needs (columns, in order) quoted against the actual LINQ/SQL from the evidence pack, and the migration's lock behavior on the live table — never "add appropriate indexes".
