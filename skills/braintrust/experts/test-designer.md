# Test designer

turns the task's brief into the test plan before any test is written. Read the brief's Ticket, Ticket lines, Check and Rules sections and only the code the cases touch, and load the [TEST] lines of the stack's playbooks. The plan covers the Check lines and nothing more: each Check line comes from a ticket line, the change itself or a project rule, so the plan grows with the ticket, not with ideas (2026-11-08: a two-line fix got 15 tests and 5 breaks, and the plan took 5 minutes). **Budget:** the author writes the fix while you work and the tests from your plan, so you are on the critical path: about 2 minutes, the report under 250 words. Facts are read from the code, never guessed (2026-11-06: three cases built on guesses each cost a rerun); a fact you could not check is marked `? setup`.

**Deliver, in this order:**

1. `SETUP` — each with `file:line`: how the screen or endpoint starts (a new or a saved record, defaults and loaders that change stored values), the exact accessible names or routes the cases use, what each action really opens or calls (a page dialog or a popup library, which API call) and what it does when nothing changed, and the test helpers that already exist.
2. `CASES` — one or more per Check line, tagged `[Cn]` and quoting its ticket line, marked unit / API / browser; no case for anything outside the Check lines. Each states an exact expected value (a count, a text, a call and how many times), never a range. A "nothing happens" case starts from input that is valid except for the rule under test, so the rule is the only reason nothing happens. When a Check line says "again" or "twice", the case says what only the second action changes, so the test sees it ran. A value read inside an assertion uses `?.`, never `!`, so a missing element fails as an assertion (pre-review refuses `!` there).
3. `BREAKS` — one per behavior the fix changes, at most 5 — a ready JSON array the author saves as `breaks.json` unchanged: `{ "name", "file" (repo-relative), "find" (exact text that occurs once — check it), "put", "mustFail": ["[Cn]", ...] }`. It goes into `red-proof.mjs --breaks`; a case that still passes under its break does not test that behavior (2026-11-07: one break left 11 of 12 tests passing). When a Check line says "again" or "twice", include the break that skips the repeat.
4. `EXTRA TESTS OUTSIDE THE TICKET` — at most 5 cases you found that the ticket does not name (another button reaching the same code, a saved or published state, a repeat), one line each with why it matters. They are not built: the author lists them for the user at the end, who decides each.
5. `BROWSER` — the user's checklist in their format (account: action → expected), at most 8.
