# Expert learning after boss feedback

Use this only when the boss identifies a concrete gap in an expert's report. Resolve findings that affect the current task through the normal review and gate. Expert coaching and skill-file improvement are separate maintenance: run them only after the PR is open and the task handoff has been delivered. They do not block implementation, the gate, PR creation or that handoff. No extra panel or new audit.

1. During its existing review, the boss records a brief pending coaching note in the existing decision/evidence record: the specific miss, supporting source/test/request evidence, why it matters, the required correction, and the proposed future check. Mark uncertainty explicitly. Reuse the finding's evidence; do not start a skill-improvement follow-up now. Retain this pending note in the conversation or existing session evidence, not a new project-memory lesson.
2. First complete the task's required corrections, verification and approved publishing flow. Opening a PR alone is insufficient if required task work remains. After the PR is open and the task handoff is delivered, resume the pending coaching as maintenance. Reuse the expert's existing corrected finding and the boss's assessment. Only if the guidance correction still needs clarification, ask the responsible expert for the smallest useful change; it may challenge mistaken feedback with evidence. Do not repeat answered or exhausted requests. If publishing is pending, fails or is not requested, leave coaching pending; do not create a PR just to trigger learning. No background execution is implied: if the session ends, report the pending maintenance honestly.
3. During maintenance, reuse the boss's supported coaching note and any completed correction assessment; request only a missing targeted assessment, never another full review. The executor verifies the supporting evidence before treating the lesson as established; a boss assertion or several agents agreeing is insufficient. Reuse valid observations, and run a targeted check only when evidence is missing. No fabricated lesson or automatic rewrite after every disagreement.
4. When validated feedback reveals missing or inadequate expert instructions, the executor fixes the responsible expert's own linked skill guidance file under `experts/`. This file is the durable destination for expert improvement; do not substitute a project-memory entry or duplicate the lesson there. Keep the change within that role's responsibility. For a miss discovered in one project, extract the missing check and state its applicability (for example, only for MySQL startup migrations); do not turn a conditional check into a universal requirement. Raw project facts remain evidence for the current task, not shared skill instructions.
5. Before editing, read the complete affected guidance and search for an existing equivalent rule. If the rule already covers the miss, diagnose why it was overlooked: correct a missing guide handoff or clarify ambiguous wording rather than append the same rule. Merge overlapping lessons. Use one concise entry containing trigger, required check, evidence reference/date and scope; keep secrets, personal data and private project details out of shared guides. Do not store raw conversations or reports there.
6. Persist the expert skill-file correction during this post-handoff maintenance, never as a task-completion or PR-creation prerequisite. Read back the edited guidance and check it against the actual corrected case. Report the changed path and lesson in a separate short maintenance update; do not delay the task handoff or edit the PR for internal expert learning. Do not rerun cleared experts or the whole panel for a guidance edit. A skill-file-only correction does not reopen the completed task. If maintenance uncovers a previously unresolved defect in the shipped change, surface it separately and follow Sanad's existing affected-scope reassessment rule; do not hide it as coaching.
7. The next invocation supplies each seated expert its updated skill guidance file, and supplies that same guidance to the boss. No project-memory lesson is required to carry the improvement forward. This is persistent instruction improvement, not model retraining. A future recurrence calls for fixing the ineffective instruction or handoff, not adding more duplicate text.

The user's standing authorization covers validated, scoped corrections to the expert skill guidance files through this procedure. It does not authorize changes to model/effort assignments, mandatory expert seating, hooks, permissions, global policy, review/gate requirements, or publishing. Such changes require their own user instruction. Advisors propose; the main executor alone writes. A failed save is reported as unsaved, never as a lesson already installed.
