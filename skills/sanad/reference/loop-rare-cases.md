# Loop — rare cases and details

[loop.md](loop.md) is the loop. This file holds what a normal task does not need: the timer, what a tool answer means, work split in parts, several PRs, the expert panel, the full review round and machine load. When this file and loop.md differ, loop.md wins.

## Timer

The timer starts, marks its stages and ends by itself: the first code edit starts it, `red-proof.mjs`, `pre-review.mjs`, `evidence.mjs` and a reviewer launch mark their stage, and a stop after `GATE: PASS` ends it. Its folder is named in `~/.claude/state/sanad-timer-active-<session id>`.

- **Start of the task (2026-11-17).** When a new task is routed (Sanad Step 0), run `node <gate>/sanad-timer.mjs request` once (2026-11-20: it starts the new timer itself; add `--repo <path>` when the task lives in another work tree than this folder): the task's time then starts at the user's request, and the wait for the user's "go" is counted as waiting, not work. Without it the start is a guess from the transcript, and the report marks it `(estimate)`.

- The ship brief ends with `node ~/.claude/skills/gate/scripts/sanad-timer.mjs report <folder>`. When the user asks about time, show that report; never rebuild it from memory.
- A wait for the user or a machine: `sanad-timer.mjs wait <folder> "<why>"`.
- Other work with no timer of its own: `sanad-timer.mjs pause <folder> "<what>"`, then `resume <folder>`. A paused task is resumed before its first edit.
- A review runs beside the other stages, so it is listed apart and never added to the total.

## What a tool answer means

- **Test machine.** One clone there is shared by every worktree of a repository. `REMOTE-DOWN` → ask the user before running here. `REMOTE-BUSY` (exit 11) → another folder's check or browser-check app uses the clone: wait, or stop that app (`remote-web.sh stop` in its folder). `REMOTE-DIRTY` → files there differ, untracked ones included. A check over ssh that finds other code in the clone does not start: run `remote-sync.sh`, then the check again. More in [remote-host.md](remote-host.md).
- **Warm copies.** The proof warms its own copies: a copy that never built is synced and built in the background and joins the workers when its build passes, so a proof no longer waits for a warm run. For a server change `sanad.mjs next` still prints `red-proof.mjs --repo <repo> --warm [--cwd <dir>] -- <the proof's test command>` at the task's start, for the background: the first proof then finds built copies. A server (dotnet) proof builds there without the commit id, so a new sync recompiles nothing and a break recompiles only its project. Warm again after `--drop-copies` or a Sanad install.
- **sanad.mjs.** It only prints; every command it prints is typed by the author, so the guards see it as today. `start --repo <repo> --notes <notes> [--base <ref>] [--engine claude|codex] [--side <name> [--cwd <dir>] -- <test command>]` saves the task. `next` prints the steps that are due (`--last`: the last round, with the full proof and the suite); `status` the real numbers (the proof's `k of n`, rounds, open notes); `ready` the required list for this tree, each item done or not done; `pr-body` the evidence block of the PR text; `owed` what a push the user ordered left open. A step is done only by a saved record of the current tree, never by a mark.
- **The user's switches.** The owner said yes to the first four on 2026-11-19 ("yes all the goal speed and quilty"). The user sets each with `git config`; the author never sets one. `sanad.stopRound <n>`: review rounds stop after round 2 (owner's yes; the tool uses 3 when the switch is not set); from then on every note but a Blocker, a security note or a ticket-line note goes to the owner in one list (fix now, or a known limit in the ship brief), and only those three open another round. `sanad.testsOnlyLane true`: the tests-only path (tests pass, one review, no breaks, no second look). `sanad.designChoice true`: the user chooses between two designs before a big design is built. Limits that stay with every one of them: a Blocker, a security note or a ticket-line note always reopens a round; a fix that changes access, saved data or a promised outcome is always re-checked; a real bug tied to the ticket is still fixed. `sanad.lateCheckLines false` (on by default since 2026-11-20): turns off the late rule; the second look then waits for the check lines, and any later check line makes the list stale. `sanad.carryDecision true`: an earlier answer may close a later note (Note check, below). The review starts when the proof log shows the passing run and the old-code run, while the breaks finish (the default since 2026-11-22; no switch). With every switch off, the loop runs by the rules it had before the switches.
- **notes.mjs.** `list --open` is the notes the guards hold open, with the guards' numbers; notes on one file and line form a group `G<k>`. `answer --fixed N19,G3 --what "<what changed and its test>"`, `answer --user N12 --decision D3` and `answer --refuted N7` print the `NOTE <n>:` lines only when the guards would accept them; else the guard's reason, and exit 1. `decide --kind note --words "<the user's exact words>" --for N12 --notes <notes>` saves the user's words once as `D<k>` (other kinds: `design`, `drop-line`, `one-job`, `outside`, `push-now`). `ask` prints one ASK NOW list as soon as a report arrives: each Question, each note that asks the user, each `(RARE)` note with no decision. `verdict --review` and `verdict --gate --tests <passed>/<run> --build "<real result>" --attack "<real result>" --security "<real result>" --ran "<real result>"` print the verdict line with its numbers (each gate flag carries the real result of that check; without them: GATE: INCOMPLETE); with an open note it prints FAIL and names it.
- **breaks.mjs.** `seed --breaks <notes>/breaks.json --repo <repo> --base <base>` writes one entry per new test, with `find` and `put` left empty. `add` reads the find text from the file at `--file` and `--line` (`--to <n>` for more lines) and refuses text that is not there exactly once. `red-proof.mjs --check-plan` names a half-written entry before any run (`PLAN OK` when the list is whole).
- **red-proof.mjs.**
  - The green run on the fix goes first and alone. When it fails, the proof ends there: often an older test still expects the old behavior.
  - `RED ✓` → quote its failing line. `NOT RED ✗` → the test proves nothing: rewrite it. The old code is RED only when a named test fails; a failure by a product error counts and the line says so, so check it is the bug.
  - A setup failure (element not found, type error, timeout) → fix the test. One exception: after a passing green run, an element the old code (or a break) does not render is red, shown as `? missing`; read that line and confirm the missing element is the bug. Keep `--then-green` on page proofs, or it stays SETUP.
  - A break whose named tests still pass → the tests do not isolate the rule: fix the tests, not the list.
  - `BREAK INVALID ✗` → the break does not compile or changes nothing. A break changes one rule.
  - `ENVIRONMENT ✗` (exit 6) → the database or the machine failed: `remote-preflight.sh --db`, then the same proof again. Do not touch the tests. A server proof on the test machine checks the database itself before any run (`git config sanad.remoteDbContainer`).
  - A red run still going at twice the slowest finished red run is stopped as stuck (`TIMEOUT ✗ … was stuck`, exit 5): a test with no time bound of its own. Bound it, then run again.
  - A `mustFail` text is part of a test's own title, and every test with that text must fail. Name a new test by words of its own title, not by its `[Cn]` tag: a part that matches a new test and an older one (an old ticket's `[C1]` in the same file) is refused before any run (`BREAK AMBIGUOUS`, exit 2). A part may name older tests alone, and a test's whole title is always accepted.
  - A new "nothing happens" check (not called, null, empty, zero, never) is proven only by a caught break whose `mustFail` names a test in its own test file; the old code never proves it. A proof that would leave one unproven, `--old` alone included, is refused before any run (`UNPROVEN ✗ <file>`, exit 2): add such a break.
  - A test of code that already works has no old version that fails: use `--break <file> --find <text> --put <text>` in place of `--old` and `--files`.
  - `--changed-since <ref>` (fix rounds): only the breaks whose file or named tests changed since `<ref>` run, beside green and the old code; it prints `PARTIAL ✓`, saves the result of each break for that code tree and writes no proof record. The full proof runs once, in the last round, and resumes: a break already caught on the same tree is not run again (`RESUMED: k of n`).
  - `--local` only on the user's word. `--files` names product files only.
- **lines.mjs and places.mjs.** `--no-ticket --repo <repo>` makes the commit check ask for no ticket ID on this branch. A name used in more than 40 files is too wide for the places search: name the rule, not the word. The list has one place per function that uses a name, and one per file for texts and data; a place that holds two rules is two lines far apart in one function. After the fix, `places.mjs --repo <repo> --names <names> --out <notes>/places.md --add-changed --base <base>` adds every changed function that has callers as an open place; the tool never closes one. `--set "fn:<function>=<outcome>"` fills every open place of one function.
- **The proof run.** `red-proof.mjs` runs on the test machine by itself. Format changed C# once before it (`dotnet csharpier format <files>`).
- **pre-review.mjs.** Lint and types of the changed packages, the ticket lines, the places list, new test lines, the commits (one task in one commit; a Conventional subject of at most 72 characters that ends with exactly one ticket ID; `git config sanad.ticketRequired false` for a repository without tickets; `lines.mjs --no-ticket` marks one branch as a task without a ticket), the size and the project's mechanical check (`git config sanad.mechanical`). A check it could not run shows as `NOT RUN` and fails. `--before-proof` runs every part except the proof part of the test asserts check, so the cheap fixes land before the proof. A ticket line quoted only in an older, unchanged test fails: quote it above a test this change adds or edits. A quote or a `[Cn]` tag on a skipped test does not count. A check that passed on the exact same code, base and notes files is not run again: it shows `(same code: passed at <time>)`; `--no-cache` runs every check.
- **review-brief.mjs.** `--pin` makes the review one of a named commit: it refuses while code files are not in that commit, and the re-check (`--recheck`) is made from that commit to the new one. `--proof-log` once per proof (server and page), and only when the log exists: before the proof (the run that writes the Test designer's launch) and on a text-only change leave it out; a path that does not exist is a usage error that names it (2026-11-18: a missing log was dropped without a word). The chosen `--size` and `--engine` are saved in the notes folder (`size.txt`, `engine.txt`): a later run without them uses the saved choice, and the size is never smaller than it. It pins the diff to the merge base, lists every changed file and the places list, adds the open outside items (`git config sanad.outsideList`), and uses the larger of the routed and the measured size.
- **size-check.mjs.** Callers are counted by the declaring type (C#) and the import path (JS). A change in a file named like an access file, or under an Auth or Security folder, is an access change. Before code, `--names` reads each named function in the planned files whole (its attributes, signature and body) by the same rules as a diff; a hit names `file:Function`, and `not read` lists the names with no definition there. Without `--names` the plan reads file names only and prints a `hint:` line.
- **evidence.mjs.** The project's spec script writes the specs (EduQuest: `check-specs.mjs <notes>/specs`). A failed check prints its totals and failing tests above its receipt. `CHECK_RERUN` → every failure is a test timeout, in test files the change does not touch: send its `CHECK RETIRED` line alone, in a text-only message, then run the printed replacement exactly; it must pass. Any other failure gets no offer: fix it.
- **Locks.** A check lock counts only while the process that wrote it still holds its id; an id taken by a newer process is stale (the edit guard, `REMOTE-BUSY`, pre-review's sync).
- **Stop and push guards.** A switch, pull, merge, reset or checkout that leaves a clean tree equal to a remote branch tip is not an edit. A check whose exit code is hidden (`| head`, `| grep`, `; echo`, `$(…)`) counts only when its output shows the runner's own pass line: run checks plainly. A `red-proof.mjs --then-green` run whose green run passed counts for the stop guard even with its output in a file (it keeps a run record); never for the push guard. A red run is cleared by the same command passing. Edits by helper agents, deleted code files and formatter runs count as edits. A command sent through ssh or a here-document is read like a local one.

## Work split in parts

- **Exact briefs.** Before a helper gets a fix, the main session finds the cause and writes the exact files and the exact change; the helper applies it, tests it and reports. "Find out why" is for real unknowns only, and the brief says so.
- **Tests beside the code.** A `sonnet-worker` may write the tests from the check lines and breaks while the main session writes the fix; one helper per test file, launched in one message, each running only its own file. Its brief carries the `[Cn]` tag, the check line and the verbatim ticket lines to quote. The main session reads and owns that diff. A new test that fails on working code may be a real bug: it goes back to the main session.
- **Fast test loop.** Every helper runs only its touched test files and reuses the build output folder: never clean it, and skip restore when no dependency changed.
- **Review finished parts early.** A finished part gets a scoped re-check on its own commits while the other parts are built. After the join, prove the merge added nothing (`git show --cc <merge>` empty, or equal `git patch-id --stable` before and after); only conflict edits then need a review. An early re-check never replaces the review that completes after the last change.
- **Joins of a dependent PR** (one marked `depends on #n`, started after that one merged; open PRs are never stacked). A join that needed conflict edits is reviewed on `git show --remerge-diff <merge>` as soon as it is committed. One full suite then runs on the top branch.
- **A requested review of a whole PR** is [full-pr-review.md](full-pr-review.md): one session per PR. A re-check's PASS covers only its scope: report it as "this fix passed", never "this PR passed".

## Several PRs

One PR per ticket by default. The plan is shown before code and waits for the user's OK (loop.md Step 1).

- One job per PR (loop.md, Size): over the line, the user decides "split it, or keep it as one job"; never the author. A keep also puts a `One job: <why>` line in the PR text.
- Shared contracts and expand-only migrations go in the first PR that needs them. Split backend and frontend when both are large.
- Each PR builds, passes its tests and is safe to merge alone. No PR shows users a half-built feature.
- PRs are independent: each starts from the integration branch. A PR that really needs another one is marked `depends on #n` and starts only after that one is merged. No stacks of open PRs.
- A series carries its order in the title (`[n/N]`). A PR that grows past the limits is re-planned with the user.

## The expert panel (Big)

- After the size line, launch the fact checks, the panel and the Test designer ([test-designer.md](../../braintrust/experts/test-designer.md)) in one message, and read the code while they work. The designer's `SETUP`, `CASES` and `BREAKS` become the tests and `breaks.json`; its `EXTRA TESTS OUTSIDE THE TICKET` are notes for the user, like a reviewer's. Save its report as `<notes>/test-designer.md`: `review-brief.mjs` then leaves the designer out of the review launches (it ran already); it comes back only for a requirement that changed after the plan.
- **Two competing designs (2026-11-17).** Two Architect seats, launched in the same message and blind to each other: one starts from the repo's own way of doing this kind of job (the `J<n>` lines: reuse first), the other from the user's goal with a free hand (the simplest design that meets every ticket line). Neither sees the author's design. The boss scores both against the ticket lines, the risk and the cost, picks one, and may take the best part of the other; the losing design and why it lost stay in the decision record. When the user chooses between the two (loop.md Step 2, only with `git config sanad.designChoice true`), both are shown in six lines: lines of code, new tables, rough hours.
- Every seat's brief carries its cap: 40 tool uses, probes on the test machine, no scan of the whole repository (no time cap, owner 2026-11-22).
- Database optimizer (a database change): its `DB SWEEP` is the database verdict. Security auditor (a security change): its `SEC SWEEP` is the security verdict. Every `→ finding` becomes a proof at the gate; every `? unchecked` is named at the gate.
- The decision record is the plan. Deviating from it means saying so and why, in one line. A new fact that breaks the plan goes back to the same boss.
- At the gate, the standing proofs: an index in the same migration for every new WHERE, JOIN or ORDER BY column, the generated SQL quoted, no I/O inside a transaction, a stable unique order for every list; anonymous → 401, wrong role → 403, not owner → 404/403, missing anti-forgery → rejected.

## Note check — before any fix (2026-11-17)

A wrong reviewer note costs a full fix round. Before fixing, one read-only agent tries to disprove every note of the round.

- **A reviewer's test** (2026-11-22, owner). A Bug or a Blocker may bring its test as code in a fenced block. Add it and run it on the reviewed code (the pinned commit) first: it fails on its assertion → the note is confirmed and skips the note check; it passes → the note goes to the note check as below; it fails on setup (element not found, a type or build error, a timeout) → it confirms nothing: fix the test and run it again, or send the note to the note check. A `fixed` answer still needs a code change and a passing test after the note: the reviewer's test, passing on the fix, is that test. Its evidence: a bug already in the base is red on the old code, as today; a bug the fix itself brought in passes on the base, so it needs a caught break that puts the reviewed lines back, read from the pinned commit: `breaks.mjs add … --line <n> [--to <n>] --put-from <pinned commit>:<a>[-<b>] --must-fail <the reviewer's test>`.
- Save each reviewer report as a file in `<notes>` (`review-<name>.md`), then `node <gate>/note-check.mjs --brief --notes <notes> --reports <file1,file2,...> --repo <repo>` and launch the `LAUNCH` line it prints, in the same message as the first fixes of notes that are plainly right.
- Save its answer as `<notes>/note-check-report.md`, then `node <gate>/note-check.mjs --record <that file> --notes <notes>`. `--repo` must be the git repository of the change: a brief that is not bound to one (`CODE: NOT BOUND`) can show nothing about the code, so `--record` turns every `REFUTED` of it into `UNSURE` (2026-11-18).
- `CONFIRMED` notes are fixed, with their tests. An `UNSURE` note is not proven either way (2026-11-18: unproven notes were sent straight to the fix): get the missing fact first (a reproducer, or the file the checker could not read) and fix the note only when the fact holds; when it does not, give that fact to a second note check or to the user. A product choice always goes to the user ([execution.md](execution.md), scope). A `REFUTED` note is not fixed: the author closes it with `NOTE <n>: refuted — <the checker's evidence>` (user decision 2026-11-17: an independent checker may close a wrong note; the author alone never can). The guards accept that line only for a note this session's note check refuted, with evidence, and never for a `Blocker` or a `Question`: those go to the user, whose words close them.
- A reviewer's `Question` is the user's (user decision 2026-11-18: "i close it and ai reviwer talk to me"): the checker still studies it and says what the code shows and which answer it recommends; `--record` prints that under `ASK THE USER`, and only the user's words close the note.
- A check is for the code it read (2026-11-18: an old "wrong note" verdict stayed valid after the code changed). A refutation stands while the files the note and its evidence name are unchanged since the checker's launch; fixing another note in another file changes nothing. After an edit of one of those files, or a git move (merge, pull, switch, reset, stash), that note is open again and `--record` marks it `UNSURE`: run the note check again for it. The newest check wins: a later `CONFIRMED` reopens a note that was closed as refuted.
- Every note closed as refuted is listed in the ship brief with its evidence ("closed as wrong by the checker"), so the user can reopen one with a word.
- A round with one or two plain notes may skip the check: the fix is cheaper than the wait.
- **A carried decision** (only with `git config sanad.carryDecision true`). An answer the user already gave in this task may close a later note about the same thing, and only when the note check wrote `SAME <n> = <k>` for the two notes, the quoted words are in that answer, and no file either note names changed since. It never closes a Blocker, a security note or a ticket-line note; the author never links two notes; the ship brief lists each note closed this way.

## After the push (2026-11-17)

- **PR checks.** Right after the user's push, start `node <gate>/pr-watch.mjs --repo <repo>` in the background (add `--require "<job name>"` unless the repository has `git config sanad.requiredChecks`). `PASS` names the required jobs that ran and passed on the final commit → say so in one line. `NOT PROVEN` → no required job is named, or one was skipped: name it and run again; never read it as a pass. `FAIL` → it prints the failing lines: reproduce the failure in a test here, fix it through the loop, and tell the user before they merge. `NONE` on a draft → the checks start when the PR is marked ready; say so. A merge is the user's; a red or running check is named before it.
- **Review score.** `node <gate>/review-score.mjs --repo <repo> --log` prints, per reviewer seat, how many of its notes led to a change, and the checklist lines the findings fell under; its totals go on the task's line in `memory/task-metrics.md`. `--repeats` names a checklist line that keeps coming back (3 of the last 10 tasks): that one becomes a check in the project's own check script (`git config sanad.mechanical`) or a rule for the author, offered to the user in the end list. It also names a seat whose notes rarely lead to a change, for the user to drop or keep.

## The full review round (Big)

- **Risk files.** The engine's risk reviewer reads only the changed files on a sensitive boundary (access, database, money, files and URLs, shared contracts) with their callers and writers, and a trace list of inputs the author did not test. The trace list has one home: `review-brief.mjs` writes it into the brief.
- **Whole diff.** The engine's whole-diff reviewer reads every changed file against the check lines and [review-checklist.md](review-checklist.md). It starts its report with `ESCALATE: sensitive — <reason>` when it finds a boundary the risk reviewer did not cover; the risk reviewer then runs on that scope before any verdict.
- **Fresh eyes.** The risk reviewer again, with a prompt that starts `You are the independent reviewer — FRESH EYES` and holds only the user's words, the ticket, the whole PR diff, the places list and the project rules. No author claims, no earlier findings, no test results.
- **The other engine.** A Claude task adds a Codex review, a Codex task a Claude Opus review, on the machine where that engine is signed in, with the fresh-eyes inputs. Unavailable is reported as incomplete before the push, never skipped silently.
- **Author-proof inputs.** The ask is the user's own words, quoted. Everything from the author or the boss (design decisions, "known gaps", rulings) goes only under `Author claims — attack these`.
- All of them launch in one message; one batched fix round covers every note. Reviewers advise and never edit. An unfinished reviewer is reported incomplete, never invented.

## Machine load

- Agents think on the API; builds and tests load the machine. Start every independent part at once and keep adding while CPU stays under about 80% and free memory above about 2 GB.
- Full suites are the heavy load: at most 2 at once on one machine, one at a time when they share a database. Check free memory first.
- No source edit while a full suite runs: the evidence helper refuses a run whose files changed under it. Hold the fixes, apply them in one batch, run once more.
- A suite never runs beside reviewers on this machine. On the test machine it does: the final suite starts with the last re-check (loop.md Step 3, item 6).
