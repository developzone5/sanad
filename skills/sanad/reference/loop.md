# Sanad implementation loop — Steps 1–5

Loaded by the `sanad-implementation` stage for substantive implementation. "Sanad Step N" anywhere refers to the step of that number in this file. Resolve relative links against this directory.

## Step 1 — Impact triage (before convening)

Two one-liners scope the DB and security checks. Reuse the routing assessment from [boss-routing.md](boss-routing.md) (self-route or boss), including its evidence and open facts; do not repeat the initial scan. The boss selects whether braintrust is needed. Material DB/security risk or unresolved design uncertainty requires the braintrust route. When convened, these one-liners decide the auditor seats: Database optimizer when DB impact is not `no`, Security auditor when security impact is `yes`. Relevant checks remain required when no advisors are needed:
- **DB impact** — does the task plausibly touch the database (schema/migrations, EF/LINQ or raw SQL, indexes, transactions, pagination, data volume/growth)? `DB impact: yes — new column + hot-path query`. If no new SQL: `DB impact: reuse-only — optimizer verifies reused queries at the new scale`.
- **Security impact** — does it touch auth, data access, money, file/URL handling, or user input (the CLAUDE.md security triggers)? `Security impact: yes — new owned-resource endpoint`.

## Step 1.5 — Check the facts (before designing)

List every fact the design depends on that lives outside the code being changed: another system's contract (the claims an identity provider really sends, a provider's response shape, a webhook payload), real data (rows written before this change, nulls, blanks, duplicates, volume), and environment or configuration. For each one:

- **Look before you sample.** Search the repo, the specs and the project's memory for what is already recorded about that fact. A recorded observation of the target environment outranks a vendor default, a local fixture or a plausible guess — a design that contradicts one stops here.
- **Prove it with a real, dated sample from the target environment** — the normal case AND the missing / empty / false case. One positive sample does not prove a universal guarantee.
- **Handle the sample safely.** Decode sensitive material locally; never paste a token or credential into an external site; keep only the minimum non-identifying shape, with the environment and the observation date.
- **Cannot prove it now → it is an open assumption**, written into `Done means` by name for the user to accept. Never silently treated as true, and never a reason to loosen a check to make the flow work.

The proven and open facts go verbatim into the braintrust evidence pack (Step 2) and the review request (Step 3.5).

## Step 2 — Braintrust the approach

For the `review` route, record the bounded approach, `Done means` and touch list, then continue to Step 3 without a panel. Convene `/braintrust` before coding when the boss selected `braintrust`, or when explicitly requested. Specialists use xhigh on their seat model (Opus 5.5 deep-risk seats, Sonnet 5.5 practical seats, per braintrust); resume the same separate Fable 5.1 / xhigh routing boss to review every report before the final decision. Preserve its route assessment and evidence rather than starting a second boss. When a panel is required, the design stage needs its complete verdict; material gaps remain incomplete. The boss records verified expert omissions with the existing evidence. Resolve findings affecting this task now; defer expert coaching and corrections to the expert's own skill file until the PR is open and the task handoff is delivered, through [expert-learning.md](../../braintrust/reference/expert-learning.md). Reuse unaffected reports; pending skill maintenance does not block task completion. The panel is picked by `/braintrust`'s seat rules (Step 1 there): experts for the actual open questions, stated in one line; a user `effort=` override passes through untouched. **The Step 1 triage decides the auditor seats**, and a seated auditor's domain is checked by that expert, not re-derived by you:
- **Database optimizer** — seated when DB impact is not `no`; its `DB SWEEP` is the authoritative DB verdict. On reuse-only tasks its job is verifying the reused queries (indexed, no N+1, sane pagination) at the new page/feature's scale.
- **Security auditor** — seated when security impact is `yes`; its `SEC SWEEP` is the authoritative security verdict.
An unseated domain still gets its standing checks at the gate.

Carry every `→ finding` from either sweep forward — each becomes a mandatory proof at the gate. The synthesis + decision record becomes the plan of record for Step 3. It carries a **touch list**: every other caller, writer, role, screen, locale and background path the change reaches — each one covered by a `Done means` line or named out of scope. Prefer the narrowest change that satisfies the ask; a model-wide or cross-cutting change needs a stated reason and proof for every writer it affects. **The synthesis ends with the `Done means` list** (3–8 checkable lines, per `/braintrust` Step 6) — that list is the contract for this task: Step 3.5's auditor checks coverage per line, `/gate` ticks each line with evidence. Write it into the spec's `## Done means` section if a spec exists.

**Boss routing replaces the every-bug panel rule (user choice 2026-09-21):** small, understood changes with no sensitive boundary may use `review`; cosmetic/mechanical edits may use `direct`. Complex, substantial, uncertain or sensitive work uses `braintrust`. Reuse the completed routing/design decision for an unchanged task; ask the same boss to reassess only when new scope, risk or evidence invalidates it, preserving completed work. Teaching, questions, checks without implementation, standalone reviews and docs stay direct without a boss call. Equivalent promotions retain the promotion evidence-reuse rule.

## Step 3 — Implement

Browser acceptance belongs to the user by default (2026-09-21). Apply [behavior-proof.md](../../gate/reference/behavior-proof.md): supply the URL/account and checklist, record their actual result, and leave acceptance pending until confirmed. Browser-only reproduction follows that manual evidence rule; required automated code/API/security/provider checks remain. Do not create browser automation solely to satisfy the review.

Build per CLAUDE.md — Read before you touch, Backend bar, ship finished code. **Touching DB writes, migrations, transactions, background workers, or exports → load `~/.claude/skills/sanad/reference/backend-scaling.md` first** (the multi-instance concurrency, query/transaction scaling, and crash-loop-safe migration rules live there; CLAUDE.md keeps only the headlines). The boss-selected route and recorded approach (including the braintrust decision when convened) are the plan: deviating mid-build means saying so and why in one line, not silently drifting. A new fact that invalidates the route or decision → targeted reassessment by the same boss with the new evidence before continuing; don't hammer forward.

**Prove the change where it can fail.** Tests go through the public entry point — the real request pipeline with its validation, binding and authorization, not the service alone; one test per lifecycle state of the record a new rule touches (the states the ask never named are where a rule gets widened by accident); and for every new or changed failure handler, one failure it was NOT written for, asserting no success side effect after a failed write.

**Format once, then verify (user choice 2026-09-28).** When the edit batch is complete and before the final checks, format the changed C# files once from the directory that owns the CSharpier manifest (`dotnet csharpier format <changed .cs files>`), then re-read any file you will edit again. There is no per-edit formatter; the commit guard still refuses unformatted or partly staged C# files.

## Step 3.5 — Independent review (fresh eyes, before the gate)

Before freezing source, synchronize with the integration branch using [execution.md](execution.md), finalize tracked bookkeeping, and collect affected tests. Before `/gate`, launch **the independent Claude reviewer** automatically (user choice 2026-09-28: Codex removed). It is one fresh subagent through the host Agent tool, chosen by risk (user choice 2026-09-30): `routine` → `subagent_type: "routine-reviewer"` (`~/.claude/agents/routine-reviewer.md` pins Sonnet 5.5 at xhigh with no Edit/Write); `sensitive` → `subagent_type: "independent-reviewer"` (`~/.claude/agents/independent-reviewer.md` pins Opus 5.5 at xhigh with no Edit/Write). The Agent tool cannot set effort per call. If the Sonnet reviewer's report starts `ESCALATE: sensitive`, relaunch the review on `independent-reviewer` against the same source before any `REVIEW:` line; the Sonnet report alone then does not back a verdict. It runs with no conversation history beyond the review request. **The prompt's first words are `You are the independent reviewer`**: the push guard credits only such a run, launched (or continued with SendMessage) after the last change and completed before the `REVIEW:` line. It covers bug hunting, the requirements/behavior template below and relevant DB/security risks for both routine and sensitive changes. State the risk in the request: `routine` for settled changes without sensitive boundaries; `sensitive` for auth/tenant isolation, DB/query/migrations/concurrency, money, file/URL trust boundaries, security-sensitive dependencies or unresolved cross-component behavior, where it must trace every caller/writer before answering. Keep the request short: the inputs below and the changed files, not the conversation. **Ready check before launch (user choice 2026-09-28):** launch only when the verbatim ask, `Done means`, the changed-file list, the focused test commands with their results, and the known gaps/open assumptions are all in hand; collect a missing one first, because a reviewer started without them comes back incomplete. Follow-ups re-check only the fix diff and its affected callers, reusing earlier coverage (Handling, below). Add Fable / xhigh only for a named unresolved issue or expertise gap, with the specific question and affected scope recorded before launch; sensitive risk alone does not trigger it. The extra reviewer examines that gap and its necessary callers/interactions, reusing completed evidence instead of repeating the whole review. Reviewers advise only; Claude alone edits. A short diff does not lower risk. Collect focused tests before review, and pause source edits while it runs. Give each reviewer: the original ask verbatim, the boss route and recorded approach (braintrust decision when convened) + the **Done means** list, every `→ finding` / `? unchecked` line from the DB and SEC sweeps, the diff (`git diff <base>...HEAD` plus uncommitted changes), and the project's `memory/missed-bugs.md` (the classes of bugs that slipped past earlier reviews — each one is a standing check).

**Author-proof inputs.** The reviewer must not be steered by the author's framing. The original ask is the user's own words, copied verbatim and quoted — never a paraphrase. Author decisions go under the heading `Author claims — attack these`; a claim is marked user-approved only with the user's verbatim chat message beside it, and everything else is a hypothesis to falsify. Do not describe the baseline for the reviewer: tell it to read the pinned base itself (`git show <base>:<path>`) for every changed rule, validator and handler, and to report any behaviour change the ask did not request. The Step 1.5 facts go in as listed — proven with their sample, open as open.

1. **Bug hunter** — the Claude reviewer above. This fills the independent review role. An additional `/code-review` run is only needed for an uncovered domain or an explicit user request. Trace changed eligibility and state transitions through downstream consumers, not just the immediate return value. Claude confirms runtime evidence. Disposition every finding as `fixed`, `accepted by user`, `follow-up: outside scope`, or `rejected: evidence`. **A confirmed correctness bug — including a rare one (retry, race, ambiguous commit) — is `fixed` in the same round, without asking the user (user rule 2026-10-06).** The author never self-accepts it ("analytics only", "rare", "info") and never parks it as a question; `accepted by user` needs the user's verbatim words and applies only to product/scope trade-offs. A reviewer's claim that something is absent ("no test harness", "no other caller") is grep-checked before it is relied on; distinguish conditional external assumptions from verified local behavior. A newly reachable dangerous path is in scope even when the underlying line predates the branch.
2. **Requirements auditor / behavior reviewer** — this is another responsibility of the same Claude reviewer, not a second automatic agent. It covers this template for both routine and sensitive changes. If a specific unresolved issue or expertise gap requires Fable / xhigh, provide fresh review context, the original request, the exact gap, the relevant source and completed evidence; request only the applicable template items for that gap. The reviewer returns the full template with `file:line` evidence on every line, and ends with its recommended `REVIEW: PASS|FAIL` and the open findings:
   - `COVERAGE:` one line per **Done means** item — `✓ implemented + tested (<test name>)` / `~ implemented, NO test` / `✗ missing`.
   - `MISSED:` what the ask or decision implies that nothing in the diff addresses — the other call sites, the other locale, the other role, the raw-SQL twin of a LINQ change, the FE surface that renders the new field, the paged list reused as a data source.
   - `HALF-DONE:` stubs, TODOs without an id, unhandled branches (null / empty / failure), fields an update endpoint silently drops, helpers defined but never called.
   - `CALLERS:` for every changed or newly-parameterized method — each caller (`file:line`), what it passes (the whole list it has, or only the changed ids?), and whether it runs under HTTP or a background service / worker. A service that starts reading the current user must be constructed on an acting user by every non-HTTP caller (`grep BackgroundServices/` for its interface).
   - `ENTRY POINTS:` every user-facing way to trigger the changed behavior — button, link/anchor, card or row click, keyboard path, tour/demo/sample path, other API callers, background jobs — each with `file:line` and `tested` / `user checklist` / `out of scope: <why>`. A sibling control that reaches the same feature by another route (an anchor that opens the item without the handler the button calls) is its own entry point; one tested control does not cover it.
   - `REMOVED:` every test or assertion deleted or weakened in the diff, with the rule change that justifies it as stated in the PR body. A deleted assertion with no stated rule change = FAIL — a red test is a rule telling you something, not friction.
   - `WRITERS:` for shared entity/model/concurrency changes, every writer including other features, login updates, jobs and bulk/raw SQL; explain whether the new rule changes its success or failure path.
   - `MEANING:` for every user-visible number, ranking or threshold whose inputs change (a new writer, a changed read query, a new data source, seed/demo data shaped differently from what production now writes): `one unit = <before> → <after>`, and the test where one actor repeats the action N times beside N actors doing it once — the ranking/threshold must follow the stated unit unless the ask says otherwise. A label that no longer names the unit is a finding.
   - `FAILURES / LOCALES:` matching and non-matching exceptions, zero-row writes, null/empty/whitespace, nested retry failure, and side effects after failed writes; each new API error code resolved in both EN and AR and traced to its consumer.
   - `HYGIENE:` literals that duplicate an existing constant or entity/column default, one rule hand-copied in two places that can drift apart, test resources (temporary databases, files, containers) not released on a failure path. Cheap ones are fixed in the same round; the rest are named.
   - `CI-SKIPPED:` every changed path whose only proof is an opt-in test that CI skips (environment-gated real-provider or integration tests): the local command run after the last edit with its quoted result (a skip is not a pass), and the PR-body note that CI does not run it. Missing → open.
   - `MISSED-BUG CLASSES:` each relevant CLASS/CATCH mapped to required automated test evidence or the explicitly user-owned browser acceptance record, with its actual before/after result and owner. Explain non-applicability for other classes. Missing tests or proof remain open; runtime evidence is owned by the author at the gate.

Read `~/.claude/skills/gate/reference/behavior-proof.md`. The behavior reviewer derives scenarios from the original request before inspecting the author's tests, exercises applicable sibling paths, roles, locales, real provider and data limits, and supplies observed evidence for each `Done means` item. A test-name list without the behavior it proves is insufficient. Use this review assignment; add a specialist only for a domain it cannot cover. Missing runtime/provider evidence is checked by the executor at the gate; a static review never substitutes for it. Collect the reviewer's actual report from its completion notification; report an unavailable or unfinished reviewer honestly and do not invent its verdict.

**Handling:** collect the required independent reviews together against frozen source, then resolve their findings in one batch. Fix confirmed in-scope bugs and missing required behavior/proof. Queue optional improvements and unrelated pre-existing debt; do not silently change an accepted product decision. For follow-up, continue the **same reviewer agent** (SendMessage to its ID) with the fix diff, finding dispositions, affected callers and new test results; it re-checks only the changed paths, affected callers and interactions, reusing its earlier coverage. Fix-round count alone does not restart full review. Start a fresh full review when boundaries, requirements or coverage change, or when the agent is no longer reachable. Any extra Fable reviewer follows only its assigned gap and affected interactions on that same source snapshot; do not copy the full assignment to it. Preserve the reviewer's agent ID and checked scope in the task handoff. A remaining blocker stays FAIL; a broader review does not clear it without evidence.

**Verdict line (mandatory for outgoing code; changed-line count is not a risk measure):** `REVIEW: PASS|FAIL — bugs <found>/<fixed>, coverage <k>/<k> ✓, untested <n>, open: <none|list>`. FAIL = something is open that the user must decide on; say what. **Emit the verdict line at the start of a line, plain (not bold, not in backticks), in a text-only message with no tool call in it** — the push guard reads the transcript, and text sent alongside a tool call is not always persisted.

## Step 4 — Gate

Invoke `/gate` — full Definition of Done + security checklist, real quoted output. **The sweeps add mandatory proofs:**
- **DB impact:** every `DB SWEEP` `→ finding` proven addressed, plus the standing four — index in the SAME migration for every new/changed WHERE/JOIN/ORDER BY column; generated SQL quoted (no N+1); transactions hold no external I/O; pagination has a stable unique order.
- **Security impact:** every `SEC SWEEP` `→ finding` proven addressed, plus the standing negative tests — anonymous→401, wrong-role→403, not-owner→404/403 (IDOR probe), missing anti-forgery→rejected. "I added authorization" is not proof; a passing 403/IDOR test is.
- **`? unchecked` sweep lines are debts, not waivers:** each one is either checked at the gate or named in the gate verdict with why it could not be checked — never silently dropped.
- **Done means:** every line of the list ticked with its evidence (the test name, the request + status, the rendered screen) — `criteria <k>/<k>` in the summary. A line with no evidence is ✗, not "should work".
- **Independent review:** the `REVIEW:` verdict postdates the last code edit. A gate-time code change (a missing test, a fix) goes back through a scoped Step 3.5 before the gate re-runs.

Red gate → back to Step 3, fix, re-gate. Never carry a red gate forward.

## Step 5 — Ask to ship

Present the teach-back brief and ask, per `/ship` — it owns the brief format, the draft-PR flow, and the integration-branch rule. **Wait for the explicit yes.** No yes → the loop ends with the brief on the table; the decision stays the user's. A "yes" to the task was never a "yes" to the push.
