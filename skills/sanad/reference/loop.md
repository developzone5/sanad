# Sanad implementation loop — Steps 1–5

Loaded by the `sanad-implementation` stage for substantive implementation. "Sanad Step N" anywhere refers to the step of that number here. Resolve relative links against this directory. Load the other references only at the step that names them.

Use the saved engine and the actual runtime assignments in [engines.md](engines.md) throughout; child assignments inherit that choice.

## Step 1 — Impact triage

Reuse the routing assessment from [boss-routing.md](boss-routing.md) (self-route or boss), its evidence and open facts; do not repeat the scan. Two one-liners scope the DB and security checks and, when a panel is convened, decide the auditor seats (Database optimizer when DB impact is not `no`, Security auditor when security impact is `yes`). Relevant checks stay required when no advisors sit:
- **DB impact** — schema/migrations, EF/LINQ or raw SQL, indexes, transactions, pagination, data volume/growth. `DB impact: yes — new column + hot-path query`; `DB impact: reuse-only — reused queries verified at the new scale`; or `no`. A change to a query's shape is `yes`, even inside a small fix: a new, split or merged query, a changed filter, aggregate, GroupBy or subquery, or a database call moved into a loop.
- **Security impact** — auth, data access, money, file/URL handling, user input. `Security impact: yes — new owned-resource endpoint`; or `no`.

Draft `Done means`: 3–8 checkable results in the user's words, including what must NOT change, each with its proof type (test / request + status / user browser check). Read what the code does today before listing it. Unclear → one question.

**Ticket words → tests (2026-10-26).** When the ask comes with a ticket, QA report or requirement list, copy every requirement line verbatim into `Done means`, each with the test or check that proves it — extra lines stay, they are never merged away. A line that ties two things together ("the same list as", "matches", "like the teacher's") gets an equality test of the two sides, not a test of each side. (Example: "students hand in the same formats teachers attach" shipped as "the teacher list plus photos".) Save those lines, verbatim, in a lines file next to the task's notes. The test that proves a line quotes it in its name or in a comment just above it. Before review, `node ~/.claude/skills/gate/scripts/check-ticket-lines.mjs --lines <file> --repo <repo> --base origin/<integration>` must print every line `✓`. A `✗` line gets its test, or the user's verbatim words that drop it (2026-11-05: a QA bug came from "selecting it again clears it", a ticket line lost in a summary; the check found the same kind of untested line on the next ticket in about one second). On the `review` and `braintrust` routes, a task with a ticket also launches the **Test designer** seat ([test-designer.md](../../braintrust/experts/test-designer.md), the practical expert agent) at Step 1.5, in parallel with the fact checks. **One brief, one proof (2026-11-07).** Before the designer starts, write the briefs with `node ~/.claude/skills/gate/scripts/review-brief.mjs --out <notes>/brief.md --ticket <verbatim ticket and QA text> --lines <ticket lines file> --check <check lines>`. **The lines file holds every line of the ticket** — steps, Expected, Actual and the linked ticket's rows — never only the Expected line (2026-11-08: a steps line, "save as a draft/publish", was left out). **Each check line starts with its source:** `[T2]` (a ticket line, numbered as in the lines file), `[change]` (what the change itself touches) or `[rule: both languages]` (a project rule); the script refuses a ticket line no check line covers and a check line with no source. Nothing else becomes a check line: the plan grows with the ticket, not with ideas (user 2026-11-08: "check lines should come from all tickets"; a two-line fix had got 15 tests). The script numbers them C1..Cn, pins the diff to the merge base, adds the open outside items (`git config sanad.outsideList`) and the missed-bug classes (`git config sanad.missedBugs`), writes the unframed fresh-eyes brief, and writes `launch.md` with the exact launch line of the designer and of each reviewer. Never copy an older brief or type a launch prompt by hand (2026-11-07: a copied brief missed the newest rule, prompts drifted between rounds, and the designer, given other lines than the reviewers, left one untested). Launch the designer from `launch.md` (fill its Area line) and write the fix while it works. Its `EXTRA TESTS OUTSIDE THE TICKET` are not built: they go into the task's end list (below). Write the tests from its `SETUP`, `CASES` and `BREAKS` (2026-11-06: tests written before it reported missed three of its cases): each test is tagged `[Cn]` and quotes its ticket line, and test code is written with the Write or Edit tool, never inside a shell command (2026-11-07: a heredoc lost its quoting and a minute). Save its `BREAKS` JSON as `breaks.json` unchanged. Then one proof run, which is also the first test run: `node ~/.claude/skills/gate/scripts/red-proof.mjs --repo <repo> --old <base> --files <fix files> --breaks <notes>/breaks.json --then-green --log <notes>/proof.log -- <test command for the changed test files>`. With a test machine set (`git config sanad.remoteHost`), the script syncs the exact tree and runs there by itself; every run (the old code, each break, green) gets its own copy, half the machine's cores at a time. `--local` only on the user's word; `REMOTE-DOWN` (exit 4) means ask the user. (2026-11-07: the proof ran eleven times in a row on the busy desktop, about 2 minutes, although the rule said tests run on the test machine: the rule was text, the script did not follow it.) It proves the tests fail on the old code, that each break of the rule under test makes its named tests fail, and that they pass on the fix. It names why each test failed; a setup failure (element not found, type error, timeout) means fix the test, not proof. A break whose named tests still pass means those tests do not isolate the rule (another empty field also blocks the save, or a wait was already true): fix the tests, not the list. (2026-11-07: three rounds in a row a "nothing happens" check passed review that no run had ever seen fail; one deliberate break left 11 of 12 tests passing.) pre-review refuses a new "nothing happens" check that no break run proved on the test files as they are now, and a check line with no `[Cn]` test. The designer's browser list becomes the user's checklist.

**Tickets win over chat words (user rule 2026-11-05: "we stick with the tickets all the time and if i said something diffrent than tickets or in images please tell me and remind me").** When the user's words in chat differ from the ticket or its design images, quote both in one line and ask which one holds. Follow the ticket unless the user then overrides it; write an override into the PR body with the user's words.

## Step 1.5 — Check the facts

List every fact the design depends on that lives outside the code being changed: another system's contract (what an identity provider really sends, a provider's response shape, a webhook payload), real data (rows written before this change, nulls, blanks, duplicates, volume), environment or configuration. For each:
- **Look before you sample.** Search the repo, specs and project memory; a recorded observation of the target environment outranks a vendor default, a local fixture or a guess.
- **Prove it with a real, dated sample from the target environment** — the normal case AND the missing/empty/false case. One positive sample proves no universal guarantee.
- **Handle the sample safely.** Decode locally; never paste a token or credential anywhere external; keep only the minimum non-identifying shape with environment and date.
- **Cannot prove it now → an open assumption**, written into `Done means` by name for the user to accept. Never silently true, never a reason to loosen a check.
- **Old data against new rules (2026-10-29).** For every new or stricter rule on a field that already has rows (a range, a step, a required value, a date order, an allowed list), count the rows that break it in the target environment. The count is a fact here, and those rows become test data in Step 3. (Example: a new 0.25-step grade rule locked every older homework with a 150-point question out of all edits, even a title change.)

Exit: `▸ checked: <n> facts confirmed, <m> not sure yet`. Proven and open facts go verbatim into the evidence pack (Step 2) and both review prompts (Step 3.5).

## Step 2 — Design

**`review` route:** record the bounded approach, `Done means` and the touch list, then go to Step 3. No panel, with one exception.

**Database seat on every route (user rule 2026-11-05).** When DB impact is `yes`, one Database optimizer (Claude `braintrust-expert`, seat Database optimizer; Codex `sanad-expert`) reads the planned query changes before coding, even on the `review` route, and returns its `DB SWEEP`. No boss verdict is needed for this one seat. Each `→ finding` is fixed in the plan or becomes a gate proof, as on a panel. A migration, transaction or concurrency change still routes to `braintrust`. (Example: a small fix once split one report count into two queries and hid the race with a clamp. No database expert had looked, and a teammate found it.)

**`braintrust` route (or explicit request):** convene `/braintrust` before coding, sized by its seat rules — experts for the actual open questions, stated in one line; one specialist round, then the same selected-engine routing boss reviews every report and decides. Specialists run at xhigh on their engine's deep-risk or practical seat model. The design stage needs the boss's complete verdict; material gaps stay incomplete. Resolve findings affecting this task now; defer expert coaching to [expert-learning.md](../../braintrust/reference/expert-learning.md) after the PR is open. Reuse unaffected reports.
- **Database optimizer** (DB impact not `no`): its `DB SWEEP` is the authoritative DB verdict; on reuse-only tasks it verifies the reused queries (indexed, no N+1, sane pagination) at the new scale.
- **Security auditor** (security impact `yes`): its `SEC SWEEP` is the authoritative security verdict.
- An unseated domain still gets its standing checks at the gate. Every `→ finding` from either sweep becomes a mandatory proof at the gate; every `? unchecked` is a debt named at the gate, never dropped.

The decision record is the plan for Step 3. It carries a **touch list** — every other caller, writer, role, screen, locale and background path the change reaches, each covered by a `Done means` line or named out of scope — and ends with the final `Done means` (the contract: Step 3.5 checks coverage per line, `/gate` ticks each line with evidence). Prefer the narrowest change that satisfies the ask; a cross-cutting change needs a stated reason and proof for every writer it affects. Write `Done means` into the spec's `## Done means` section when a spec exists.

**PR plan before coding (user rule 2026-10-28).** For every task, ticket or sprint on the `review` or `braintrust` route, show the user how many PRs the work needs before Step 3, and wait for their OK; a `direct` edit just says `1 PR` on its size line. One line per PR: its order, the tickets it covers, what it holds, a rough size (files, changed lines of logic), its base (the integration branch) and `independent` or `depends on #n` with the reason. Sizing rules:
- One reviewable behavior per PR. Aim for at most ~400 changed lines of logic and ~30 files; tests, translations and generated files do not count toward the lines.
- Shared contracts and expand-only migrations go in the first PR that needs them. Split backend and frontend when both are large.
- Each PR builds, passes its tests and is safe to merge alone, in order. No PR shows users a half-built feature: an unfinished screen stays unlinked until the PR that completes it.
- PRs are small and independent by default (user rule 2026-10-30): each starts from the integration branch and works without any other open PR, so reviews can run at the same time. A PR that really needs another one is marked in the plan and starts only after that PR is merged. No stacks of open PRs, and each PR is reviewed before a PR that depends on it starts.
- A series of ordered PRs carries its order in the title (`[n/N]`), in the project's title pattern.
- One PR is fine for small work; say why. A PR that grows past the limits during the build is re-planned with the user before it grows further.

**Test-only items go to the lighter worker (user rule 2026-10-31).** Adding tests for code that already works does not need the strongest model: use `sonnet-worker` here, or the `tests` role on a remote host. A new test that fails may be a real bug, so it goes back to the main session or a `code` helper. All real fixes stay where they are.

**Exact briefs (user rule 2026-10-30).** Before a helper gets a fix, the main session finds the cause and writes the exact files and the exact change, so the helper only applies it, tests it and reports. "Find out why" is for real unknowns only, and the brief says so. A small text or style fix the main session makes itself. Seen 2026-10-30: 11 minutes with an exact brief, about 36 with "compare and find".

Routing replaces the every-bug panel rule (user choice 2026-09-21): small understood changes use `review`; cosmetic/mechanical edits use `direct`; complex, substantial, uncertain or sensitive work uses `braintrust`. Teaching, questions, checks, standalone reviews and docs never convene a panel.

## Step 3 — Build and prove

Load [engineering-bar.md](engineering-bar.md) (backend bar, verify-fast ladder, mechanical checks, proof by change type, self-review). **Touching DB writes, migrations, transactions, background workers or exports → load [backend-scaling.md](backend-scaling.md) first.** The recorded route and approach are the plan: deviating means saying so and why in one line. A new fact that invalidates the route → the same boss reassesses that fact before you continue.

**Remote test machine (optional; user rule 2026-11-06).** When `git config sanad.remoteHost` names one, builds, tests and full suites run there, not here. `bash ~/.claude/scripts/remote/remote-sync.sh` puts this folder's exact tree on it, without a push, uncommitted work included. Then `ssh <host> "cd /d <remote repo>\<subfolder> && <command>"` runs the command, and its output counts as verification. `REMOTE-DOWN` → ask the user before running here. `NO-REMOTE` → run here, as always. (2026-11-06: the same full suite took 143 s with 6 timeouts on the busy desktop, and 53 s on the remote.) See [remote-host.md](remote-host.md).

Build in slices: each slice is code plus its test plus the mechanical checks, committed before the next. One PR per behavior; split backend and frontend when both change substantially.

**Real-use list before code (user rule 2026-10-30).** Before coding a ticket, write its real paths as one list: role, action, result. Each screen also gets: left open for minutes, data changed by someone else meanwhile, refresh and back, two tabs, and older data saved through the new form. Each line becomes a test, written with the slice. Of 40 confirmed bugs in one release, most were these paths or a reader the rule missed.

**Every reader follows a changed rule (user rule 2026-10-30).** For a new or changed rule, list each page, report, export, dashboard and role that reads that data, including roles the ticket does not name, and give each one a test. A ticket's scope does not limit its side effects: a grade rule meant for students also reached the parent dashboard.

**Find every user by search, never from memory (2026-10-26).** For each changed or newly added component, helper, shared rule, config list, error code or state field, search its users — imports, callers, readers, copies, sibling screens, other roles' routes — and for a new piece used beside an older one (a new player next to the old preview, a new guard next to the old check), every place that uses the older one. Write the list into the task record with the search you ran: each place is changed and tested, or named unchanged on purpose with the reason. A list taken from the ticket or written by hand ("these four screens") is not a search. The mechanical checks print the sibling users they can find; each one gets a line in this list. (Example: a new video player was wired into four hand-picked screens while two other screens kept the old preview, and QA found them.)

**Prove the change where it can fail.** Tests go through the public entry point (the real request pipeline with validation, binding and authorization), one test per lifecycle state of the record a new rule touches, and for every new or changed failure handler one failure it was NOT written for, asserting no success side effect after a failed write. Bug fixes: red before green, the failing assertion quoted. Data writes: the real provider. For every new or stricter rule on an existing field, two tests on a row saved before the change that already breaks the rule: editing a different field still saves, and changing that field itself must meet the new rule.

**Prove red with the helper, never by hand (2026-10-26).** Run the new test against the old code with `node ~/.claude/skills/gate/scripts/red-proof.mjs --repo <repo> --old <commit before the fix> --files <fix files> [--cwd <dir>] -- <executable> <args>`: it swaps in the old fix files, runs the test once, always restores them byte for byte, and prints `RED ✓` (quote its failing line) or `NOT RED ✗` (the test proves nothing — rewrite it). A test of code that already works has no old version that fails: use `--break <file> --find <text> --put <text>` in place of `--old` and `--files`. It changes that text for one run and restores it (user rule 2026-10-31). Never build a broken version with low-level git commands: 3 of 9 helpers stopped on that in one round. Never type a red run as a plain test command or a "swap; test; restore" compound: the push guard keeps those as failed checks forever, and the user ends up pushing by hand.

Browser acceptance belongs to the user (2026-09-21): apply [behavior-proof.md](../../gate/reference/behavior-proof.md) — URL, account and checklist supplied, their actual result recorded, pending until confirmed. No browser automation solely to satisfy a review. **Before giving the user a URL (2026-10-26):** run the app the way the project's memory records for local testing (its own recipe — never an improvised copy on side ports), and check that the exact address the user will open answers (the browser port, status 200); quote that result. Signing in is the user's own check (user rule 2026-10-28: "its not your job to check login i will do that"). Switching the user's main working folder to another branch needs their OK first.

**Format once, then verify (2026-09-28).** When the edit batch is complete, format the changed C# files once (`dotnet csharpier format <files>` from the directory that owns the manifest), re-read any file you will edit again, then run the focused tests and the mechanical checks. Exit: `▸ built: <n> files changed, <n> tests pass, checks clean` with real output.

**Fast full suite before review (2026-10-26, user-approved).** When the project's frontend (or any other) suite runs in well under a minute, run it in full once right after the first complete build, before Step 3.5 — older tests that still pin the previous rule surface before review, not at the push. The once-per-task rule still holds for slow suites (the backend full run stays once, at the end).

**Fast test loop (user rule 2026-10-28).** While fixing, run only the touched test files (a single test file path for the frontend runner, a class-name filter for the backend), and reuse the same build output folder: never clean it, and skip restore when nothing in the dependencies changed. The wide filtered run and the full frontend suite run once at the end of each part, and once more on a joined tree only when the join had conflict edits. Every helper brief carries this rule.

## Step 3.5 — Independent review: two passes and a fresh-eyes review at once, one fix round, then a re-check (user choice 2026-10-12; fresh eyes 2026-10-26; all at once 2026-10-28)

Freeze the source: synchronize with the integration branch per [execution.md](execution.md), finalize bookkeeping, collect the focused test results. Pause source edits while reviewers run. Run every pre-review check with one command, on this folder, in parallel: `node ~/.claude/skills/gate/scripts/pre-review.mjs --was <routed size> [--lines <ticket lines file>] [--check <check lines file>]`. It covers lint and types of the changed packages, the ticket lines, new test lines (`check-test-asserts.mjs`: a range where the exact value is known, unless the line says why, `// range: <why>`; a "nothing happens" check no break run proved; a check line with no `[Cn]` test), the commits (`check-commits.mjs`, team rule 2026-11-08: one task in one commit, a Conventional subject of at most 72 characters that ends with exactly one ticket ID, e.g. `fix(homework): clear filter on second click (TUW-225)`; run it again right before the push), the size of the real change and the project's mechanical check (`git config sanad.mechanical`); a repeat type check takes seconds (2026-11-06: one by one they took 3.5 minutes, and a fixed path checked another folder). `SIZE GREW` adds the roles it names to this round. Start the full suite first, alone or on the remote test machine, and the reviewers after it; next to them it ran at a third of its speed and timed out. Every review brief carries its `callers:` line, and each listed caller is checked against the new behavior. Every brief also carries the stack line and the playbook lines for the layers the diff touches (`~/.claude/skills/braintrust/playbooks/`, the [ALL] lines plus the tags of the risk signals the size check named). **A tiny or small change gets a focused brief (2026-11-06):** trace the changed hunks, every caller in the `callers:` line and each `Done means` line; do not re-derive the whole screen or file; aim for about 15 tool calls and 2 minutes, and stop once every line is traced. A sensitive signal or a `SIZE GREW` keeps the full brief. (On a one-line fix three reviewers each took 3–3.6 minutes, the slowest step of the task.) **On a tiny or small change, start the reviewers early (2026-11-06):** as soon as the fix and its tests are written and the one red-proof run is done (it swaps files, so never while reviewers read), rerun `review-brief.mjs` with the same files plus `--proof-log <notes>/proof.log` (it adds the callers and the proof), then launch the three reviewers from `launch.md`: both fresh-eyes reviewers read the unframed brief, the whole-diff reviewer the framed one, all on the working tree against the pinned merge base. The commit, the remote sync, `pre-review` and the full suite then run while they read. Any code change after the launch gets a re-check of the changed lines; a test change first repeats the proof run. **Known outside items:** every brief lists the project's open outside findings (below) under "known, do not report again"; `review-brief.mjs` reads them from the list `git config sanad.outsideList` names, and lists apart the items in files the change touches: those are reported when this change alters or worsens them. **Every brief comes from `review-brief.mjs`**, never from a copy of an older brief; a rule a reviewer must follow on every task goes into that script's template, not only into a prompt file (agent prompt files may load only when a session starts).

**Ready check before launch (2026-09-28):** the verbatim ask, `Done means`, the changed-file list, the focused test commands with their results, the known gaps and open assumptions, the Step 1.5 facts, every sweep `→ finding` / `? unchecked`, and the project's `memory/missed-bugs.md` (each CLASS/CATCH is a standing check). A missing input is collected first; a reviewer started without it comes back incomplete.

**Author-proof inputs.** The ask is the user's own words, quoted, with the ticket or QA text verbatim when there is one. Everything that comes from the author or the boss — design decisions, "known gaps", rulings such as "client-side is fine", earlier dispositions, reasons something is out of scope — goes only under `Author claims — attack these`, never as accepted facts or settled context; a claim is user-approved only with the user's verbatim message beside it. Do not describe the baseline: tell the reviewer to read the pinned base itself (`git show <base>:<path>`) for every changed rule, validator and handler, and to report any behaviour change the ask did not request. (Example: a boss ruling and a "known gap" passed in as context let both reviewers wave through a client-clock bug.)

**Pass A — risk files.** The engine's risk reviewer (Claude `independent-reviewer`, Opus 5.5; Codex `sanad-risk-reviewer`, GPT-6 Astra), xhigh and read-only. Scope: only the changed files on a sensitive boundary — auth/tenant isolation, DB/query/migration/concurrency, money, file/URL trust, security-sensitive dependencies, shared contracts, unresolved cross-component behaviour — plus their callers and writers. Skipped when no changed file is on such a boundary (`routine` risk); run on a boundary Pass B escalates. DB impact `yes` always runs Pass A, with the `DATABASE` checklist item on every changed query. Its prompt adds a **trace list**: 5–10 concrete inputs the author did not test for — the null/empty/huge/malformed value, the other role, the other tenant, the duplicate or concurrent request, the replay after an ambiguous commit, the missing row, the dependency that fails, the opposite lifecycle state, and an existing row saved before the change that already breaks a new or stricter rule while a different field is edited. The reviewer traces each through callers, writers and downstream consumers and reports defects only.

**Pass B — whole diff.** The engine's whole-diff reviewer (Claude `routine-reviewer`, Sonnet 5.5; Codex `sanad-reviewer`, GPT-6.1 Sol), xhigh and read-only. Scope: every changed file — backend, frontend, i18n, tests, comments — checked against `Done means` and the coverage checklist below, reading the pinned base itself. It reports defects and gaps, not narration. When it finds a sensitive boundary Pass A did not cover it starts its report with `ESCALATE: sensitive — <reason>`; Pass A then runs on that scope before any verdict.

**Round 1 runs every review at once (user-approved 2026-10-26, installed 2026-10-28).** Launch Pass A, Pass B and the fresh-eyes review below together, plus a review by the other engine on every push that carries code (user rule 2026-10-29): a Claude task adds a Codex review (GPT-6 Astra, xhigh), a Codex task adds a Claude Opus review. It runs on the machine where that engine is signed in, through Orca, with its brief in a file and its report written to a file, and it gets the same unframed inputs as the fresh-eyes review. Unavailable (not signed in, no quota) is reported as incomplete before the push, never skipped silently. Then one batched fix round covers every finding from all of them. Serial rounds cost the most time and let a late reviewer force another full round. Busy agents per machine (builders and reviewers together) follow the machine, not a fixed number (user rule 2026-10-29: "we need 10 if we can"): start every independent part at once, and keep adding parts while CPU stays under about 80% and free memory above about 2 GB. Agents think on the API, so a machine's CPU is busy only during builds and tests (measured 2026-10-29: 8 helpers, CPU 45–51%, 11 GB free). Idle power is a missed speed-up (user rule 2026-10-29: "we have more powers … the goal is to finish faster"): split long work and start the checks of finished parts early to use it. The guard closes each finished helper's terminal; stop the local app stack while agents build and test. Split work into as many parts as the files allow (for a design pass, one part per screen), so the extra agents have work.

**Review finished parts early (user rule 2026-10-28).** When the work is split into parts — helpers in separate worktrees, or slices committed one by one — launch a scoped re-check on a finished part's own commits as soon as it reports, while the other parts are still being built; do not wait for the join. After the join, prove the merge added nothing (`git show --cc <merge>` empty, or equal `git patch-id --stable` of each part before and after); only conflict edits then need a review. Early re-checks count toward the machine's load limit, and they do not replace the final review: a review that completes after the last change still comes before the `REVIEW:` line.

**Check each join at once (user rule 2026-10-29).** In stacked PRs, every join that needed conflict edits (a lower branch merged into the next PR branch) is reviewed by both engines (Claude and Codex) on `git show --remerge-diff <merge>` as soon as it is committed, in parallel with the next join; do not wait for the whole chain. On 2026-10-29 a join bug made at 13:32 was found about 10 hours later and sent a fix through 3 more PRs. A chain that only carries a reviewed fix up (no conflict edits) runs no per-step tests. One full suite then runs on the top branch, which holds every fix, and CI covers the lower branches on push.

**A review is always the full review (user rule 2026-10-30).** When the user says "review", or a push needs one, run [full-pr-review.md](full-pr-review.md): one session per PR, never one session for a whole series, with the whole brief, on both engines. On 2026-10-30 one session per PR raised 33 findings on PRs where one session across all of them had found a few; all 9 ran at once in about 20 minutes. A re-check's or join check's PASS covers only its scope: report it as "this fix passed", never as "this PR passed". Every finding is a lead: confirm or dismiss it in the code, and prove each real one with a test that fails first.

**Full test runs are the heavy load (user incident 2026-10-29).** Thinking agents barely use the machine, but a full suite does: count full suites separately from agents, and start at most 2 at once on one machine, one at a time when they share a database. Six at once filled 23 GB, Windows killed the runs, and the container engine went down with them, which cost a night. Before starting a full suite, check free memory and that no other full suite is running. **No source edit while a full suite runs (2026-11-05):** the evidence helper refuses a run whose files changed under it, so an edit costs the whole run. Hold review fixes until the run ends, then fix them in one batch and run once more (twice in one day an edit mid-run cost a rerun).

Launch the round-1 reviews in one message so they run in parallel. **Every review prompt starts with `You are the independent reviewer`** — the push guard credits only such a run, launched after the last change and completed before the `REVIEW:` line. Keep each prompt to the inputs above and the changed files, never the conversation. Use the selected engine's native launch and effort controls from engines.md. The Claude push guard recognizes Claude native runs; Codex collects its own real agent IDs/results and applies the same review ordering explicitly.

**Report contract (both passes):** line 1 `RECOMMEND: PASS|FAIL`; then findings ordered by severity, one line each — `Blocker|Bug|Gap|Question — file:line — <input> → <wrong result> — <one-line fix>`; then the coverage checklist, one short line per item (`✓`, `✗ <what>`, `– n/a <why>`); then `NOT VERIFIED:` one line; then `OUTSIDE PR:` defects on paths the change neither touches, exposes nor makes reachable, one line each. A `Question` is only for what the quoted ticket, QA and spec lines leave open, and it quotes the line that leaves it open; a question those lines already answer (an "Expected" line, a rule row) is not listed, and the change is checked against that answer (2026-11-07: a reviewer asked what QA's "Expected" line already said). A defect on a path the PR adds, changes, makes visible or makes reachable is a finding above, even when the line predates the branch — never an `OUTSIDE PR` line. No traced-input essays, no restating the diff, no praise. Hard caps: 60 tool uses and 600 words per pass; stop reading when the verdict is stable.

**Handling.** Collect both reports from their completion notifications, dedupe, and disposition every finding: `fixed` / `accepted by user` (verbatim user words; product or scope trade-offs only) / `follow-up: outside scope` / `rejected: evidence`. **A confirmed correctness bug — including a rare one (retry, race, ambiguous commit) — is `fixed` in the same round, without asking (user rule 2026-10-06);** the author never self-accepts it as "rare" or "info". Grep-check any claim that something is absent before relying on it. A newly reachable dangerous path is in scope even when the line predates the branch. Cheap hygiene is fixed in the same round. Only the user parks a finding (`accepted by user` with their verbatim words); the author never parks one as "pre-existing", "user decision" or "known gap" on their own. Every `OUTSIDE PR` line goes to the user before the push as one question — fix here, separate PR, or leave — and its answer is recorded. **At the end of every task, one list: "Outside the ticket — for you to decide" (user 2026-11-08: "extra should mention in the end").** It has two parts, each one line per item: **Problems outside the ticket** (`OUTSIDE PR` lines: defects on paths the ticket does not touch) and **Extra tests outside the ticket** (the designer's `EXTRA TESTS OUTSIDE THE TICKET` and the reviewers' `EXTRA TEST` lines: more checks for this fix that the ticket does not name). Nothing on it is built or dropped without the user's word. **One outside list per project (2026-11-06):** each outside finding is written once to the project's `memory/outside-findings.md` (date · what happens · where · status: open / own PR / ticket / ignored, with the user's words), and the next review briefs list the open ones as known, so they are not reported again. The user decides each item once. (The same four old problems came back in three review rounds of one ticket.) **The PR body is checked for parked findings (2026-11-05):** before the ship brief, run `node ~/.claude/skills/gate/scripts/check-pr-body.mjs <PR body file>`. It refuses "kept as is", "author's decision", "known gap", "pre-existing", "no page reads it" and the like, unless the same line (or, for a lead line ending in ":", every bullet under it) quotes the user's own words or the ticket's. Fix the finding or get the user's words; never reword the line to pass. (Example: a PR body parked two findings the reviews had raised as "the author's decision"; a teammate found both again.)

**Re-check after fixes.** Every fix round ends with a **fresh Pass B launch** (a new agent, not a SendMessage continuation) over only the lines changed since the last pass plus their callers, carrying the dispositions and the new test results; it reuses earlier coverage. A fix on a sensitive boundary also gets a fresh scoped Pass A. The step ends when the latest pass reports zero open Blocker/Bug/Gap. Fix-round count alone never restarts the full review; changed boundaries, requirements or coverage do. Add a separate reviewer on the selected engine's boss model / xhigh only for a named unresolved issue or expertise gap, scoped to that gap, with the question and scope recorded first.

**Fresh-eyes review before every push of code (2026-10-26; promised 2026-10-19).** Delta re-checks only see the last fix, and framed prompts see the author's view. So every push that carries code gets one unframed review, launched in round 1 with the other passes: the engine's risk reviewer (Claude `independent-reviewer`, Opus 5.5; Codex `sanad-risk-reviewer`), whose prompt starts `You are the independent reviewer — FRESH EYES` and holds only the user's verbatim words, the ticket/QA text, the whole PR diff (`git diff <integration>...HEAD`, never just the last commit), the project rules and `memory/missed-bugs.md`. No author claims, no earlier findings or dispositions, no known gaps, no test results. It reviews every changed file against the ask with the full coverage checklist. Its findings join the same batched fix round and its fresh Pass B re-check. The last completed review before the `REVIEW:` line is then either this review with no finding, or the re-check of the fixes made after it. Run it again only when a fix changes behaviour beyond its findings, adds a boundary, or the PR's scope changes. (Example: an unframed re-review once found 8 bugs that both framed passes had missed.)

**Coverage checklist** (Pass B fills it all; Pass A only the lines its scope touches). Apply [behavior-proof.md](../../gate/reference/behavior-proof.md): scenarios come from the original request, not from the author's tests.

**Every change** — fill each one:
- `COVERAGE:` one line per `Done means` item — `✓ implemented + tested (<test name>)` / `~ implemented, NO test` / `✗ missing`.
- `MISSED:` what the ask or decision implies that nothing in the diff addresses — the other call site, the other locale, the other role, the raw-SQL twin of a LINQ change, the FE surface that renders the new field, the paged list reused as a data source.
- `HALF-DONE:` stubs, TODOs without an id, unhandled null/empty/failure branches, fields an update endpoint silently drops, helpers defined but never called.
- `CALLERS:` for every changed or newly-parameterized method — each caller (`file:line`), what it passes, whether it runs under HTTP or a background service. A service that starts reading the current user must be constructed on an acting user by every non-HTTP caller.
- `ENTRY POINTS:` every user-facing way to trigger the changed behavior — button, link, card or row click, keyboard path, tour/demo path, other API callers, background jobs — each `tested` / `user checklist` / `out of scope: <why>`. A sibling control that reaches the same feature by another route is its own entry point.
- `REMOVED:` every test or assertion deleted or weakened, with the rule change that justifies it as stated in the PR body. No stated rule change = FAIL.
- `HYGIENE:` literals duplicating an existing constant or default, one rule hand-copied in two places, comments naming numbers or lists the change made stale, test resources not released on a failure path.
- `SPEC WORDS:` each ticket/requirement line → the test that proves it; a line tying two things together ("same as", "matches") → an equality test of both sides. No test = Gap.
- `USERS FOUND BY SEARCH:` for every changed or new component, helper, shared rule, config list, error code or state field — the search the reviewer ran itself and every hit (imports, callers, readers, copies, sibling screens, other roles' routes; for a new piece used beside an older one, every place that uses the older one). Each hit: `changed + tested (<test>)` / `unchanged on purpose: <why>`. A hit the author's list lacks is a Gap; a hit that shows the bug the PR fixes elsewhere is a Bug.
- `EXISTING PATTERN:` search for the same problem already solved in the repo (a helper, a guard, a component); a second, different solution or a sibling left on the old one is a Gap.
- `TESTS CAN FAIL:` each new or changed test was shown red on the old code (quoted), or the reviewer explains which line of the change makes it fail without the fix. A test that passes on the old code proves nothing — Gap.
- `TYPES:` a new literal (status, code, kind, file extension list) used in more than one place has one shared constant, union or enum; two hand-copied lists are a Gap.
- `MISSED-BUG CLASSES:` each relevant CLASS/CATCH from `memory/missed-bugs.md` mapped to a named test or the user-owned browser record with its actual result; non-applicability stated for the rest.

**Only for this type of change** — the trigger is in brackets; when it does not apply, write `– n/a <why>`:
- `WRITERS:` [a shared entity, model or concurrency change] for shared entity/model/concurrency changes, every writer including other features, login updates, jobs and bulk/raw SQL, and whether the new rule changes its success or failure path.
- `MEANING:` [a user-visible number, ranking or threshold changes] for every user-visible number, ranking or threshold whose inputs change: `one unit = <before> → <after>`, and the test where one actor repeats the action N times beside N actors doing it once. A label that no longer names the unit is a finding.
- `FAILURES / LOCALES:` [a new failure path, error code or string] non-matching exceptions, zero-row writes, null/empty/whitespace, nested retry failure, side effects after failed writes; each new API error code resolved in both EN and AR and traced to its consumer; a removed `{{placeholder}}` while a caller still passes it; when a rule gets wider or narrower, its error code's server message and both locales' texts say the new rule (the mechanical check lists them).
- `OLD DATA:` [a new or stricter rule on a field with rows, or a limit that can change after the data exists] every new or stricter rule on a field that already has rows (range, step, required value, date order, allowed list), and every stored value that a later change to its limit can leave outside it (a lowered maximum) — the count of rows breaking it from Step 1.5, and the two tests: an older row that breaks the rule still saves when a different field is edited; changing that field itself meets the new rule. Every exemption in a check (an unchanged value sent back, a standing mark) is tested against EVERY clause of that check, not only the clause it was written for. Missing → Bug.
- `ACCESS PAIRS:` [a read or write of another person's data] every read or write of another person's data checks the caller against THAT record or person (caller × student, caller × section), not two separate truths; every list inside a response (students, sections, files) is filtered by the caller's own scope. Probe: two staff with different sections on one shared record.
- `CLIENT STATE:` [a page that edits or shows server state] every page that edits or shows server state — what it shows before the fresh read (a cache never seeds an editor), after a refusal, after another tab or user changes the same record, and which clock decides a deadline (the server's).
- `NEW BLOCKS:` [a new disabled button, guard or refusal] every disabled button, guard or refusal the change adds — each way out of it listed and tested (clear, retry, reload, another tab, the data changing underneath). A block with no tested way out is a Bug.
- `DATABASE:` [a method that reads or writes the database] (user rule 2026-11-05; the Database optimizer's sweep, applied to the diff) for every changed method that reads or writes the database:
  - **Round trips:** the statements it sends before (read the pinned base) and after. More statements, one aggregate split into several reads, or a clamp, cap or comment that explains a race between two reads is a Bug: two reads of one fact are one statement. The mechanical check prints every method whose database calls grew.
  - **Query shape:** no query per row or inside a loop (N+1). No EXISTS or correlated subquery inside an aggregate over a large table without a reason (the table sizes in the project's database catalog, when it has one).
  - **Indexes:** every new or changed WHERE, JOIN or ORDER BY column has an index (check the project's schema catalog, when it has one), added in the same migration. A composite index only serves a filter on its leading column; a unique index on a table with soft deletes must leave the deleted rows out.
  - **Lists:** a stable unique order and a bounded page size.
  - **Writes:** no I/O inside a transaction; a concurrent or replayed write is safe (unique constraint, guarded UPDATE, idempotency key); a total built from older rows still fits its column.
  - **Readers:** a new reader reads a table that production really writes; seed or test data can hide an empty one.
  - **Clocks in SQL:** a current-time call written inside a query, which the ORM sends to SQL, runs on the database's clock, not the app's.
  - **Real provider:** every new or changed query shape runs on the real database. In-memory tests cannot fail on SQL translation. When the statement count is the claim, a command-counting test that fails on the old code. Missing → Gap.
- `TIME:` [a rule that compares times] every rule that compares times — tests at the precision the screen shows (the first and last second of the shown minute or day, and the next one); which clock decides (server UTC, the client's wall clock, the database's clock) and both sides of each compare on the same one; one clock read per method, so two windows cannot straddle a boundary; local time only at the UI edge; a state that depends on time (open, overdue, closed) is computed from the clock, never only from a stored status. (Example: lateness judged to the second, while the screen showed minutes, marked a hand-in inside the due minute late.)
- `API FIELDS:` [a changed rule] when a rule changes, every DTO or API field that carries the same fact (a late flag, an overdue flag, a status, a count) reads the one shared rule, whether or not a page reads it today. Search the DTOs and their projections, not only the frontend callers. A field left on the old rule is a Bug unless the user accepted it in their own words. (Example: two API late flags were left on the old rule because "no page reads them"; a teammate and the fresh-eyes review both flagged them.)
- `UI:` [a changed screen] every CSS class, token or icon a changed screen uses exists in this repo; the layout holds at phone width, in RTL and with long text (a scrolling child inside a flex box needs a zero minimum size); focus stays in place when part of the screen swaps; every control works by keyboard and has a screen-reader name; contrast meets WCAG 2.1 AA; a file or media type the screen opens works in the target browsers. Proof: the code, plus a line in the user's browser checklist. (Example: four of the past escaped bugs were a missing CSS class, a flex box that overflowed, lost focus after a swap, and a video format the browser could not play.)
- `CI-SKIPPED:` [proof that lives only in an opt-in test] every changed path whose only proof is an opt-in test CI skips: the local command run after the last edit with its quoted result (a skip is not a pass), and the PR-body note. Missing → open.

Reviewers advise; the selected engine's main executor alone edits behavior code. They do not rerun builds or tests the author ran unless an evidence gap requires it; runtime and provider evidence stay with the author at the gate. An unavailable or unfinished reviewer is reported incomplete, never invented. Preserve reviewer IDs and checked scope in the task handoff.

**Verdict line (mandatory for outgoing code; changed-line count is not a risk measure):** `REVIEW: PASS|FAIL — bugs <found>/<fixed>, goals tested <k>/<k> ✓, untested <n>, open: <none|list>`, after one plain sentence for the user (Reporting contract). PASS needs `open: none` — the only exception is user-owned browser acceptance still pending, named as such — and, for a push that carries code, a completed fresh-eyes review and a completed other-engine review, each with no open finding. FAIL = something open the user must decide on; say what. Emit it at the start of a line, plain (no bold, no backticks), in a text-only message with no tool call — the push guard reads the transcript.

## Step 4 — Gate

Invoke `/gate` — the Definition of Done + security checklist with real quoted output. The sweeps add mandatory proofs:
- **DB impact:** every `DB SWEEP` `→ finding` proven addressed, plus the standing four — index in the SAME migration for every new/changed WHERE/JOIN/ORDER BY column; generated SQL quoted (no N+1); transactions hold no external I/O; pagination has a stable unique order.
- **Security impact:** every `SEC SWEEP` `→ finding` proven addressed, plus the standing negative tests — anonymous→401, wrong-role→403, not-owner→404/403 (IDOR probe), missing anti-forgery→rejected.
- **`? unchecked` lines are debts:** each checked at the gate or named in the verdict with why it could not be.
- **Done means:** every line ticked with its evidence — `goals <k>/<k>`. No evidence = ✗.
- **Independent review:** the `REVIEW:` verdict postdates the last code edit. A gate-time code change goes back through a scoped Step 3.5 re-check before the gate re-runs.

Red gate → back to Step 3, fix, re-gate. Never carry a red gate forward.

## Step 5 — Ask to ship

Present the teach-back brief and ask, per `/ship` — it owns the brief, the draft-PR flow and the integration-branch rule. **Wait for the explicit yes.** No yes → the loop ends with the brief on the table. A "yes" to the task was never a "yes" to the push. After the push, log the task line in `memory/task-metrics.md` (blockers found after push start at 0 and are the quality metric).
